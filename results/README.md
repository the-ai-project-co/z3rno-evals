# `results/` — eval run artifacts

The baseline `results.json` in this directory was generated by running
the harness against a **local z3rno-server with no LLM key**. It is
the honest "stub-only" floor:

| Metric | Baseline |
|---|---|
| `recall@k` (content) | 0.300 |
| `mean_mrr` | NaN (ID-based; we use content recall now) |
| `entity_coverage` | 0.300 |
| `faithfulness` (stub judge) | 0.375 |
| `p50_latency_ms` | 16.6 |
| `p95_latency_ms` | 19154.8 |

The p95 number is dominated by VECTOR queries timing out on embedding
generation when no `OPENAI_API_KEY` is set. With a real key those drop
to single-digit-ms.

The numbers will only improve once:

1. `OPENAI_API_KEY` (or `LLM_API_KEY`) is exported on the server, so
   VECTOR / AUTO / TRIPLET / ASK / TRACE actually work.
2. The seed data is richer (today we seed 10 deterministic memories;
   our test stack happened to have 22K from prior runs, which means
   some lexical queries hit unrelated memos first).
3. Phase A + Phase D run end-to-end (DISTILL_ENABLED + REFINE_ENABLED)
   so the GRAPH / CODE / TRACE strategies have a graph to traverse.

**Regression-gate semantics:** until the CI workflow produces a
post-LLM-key baseline, any PR that improves *or* degrades these
numbers will trigger the regression detector. That's fine — every
delta vs. this floor is worth seeing.

Replace this baseline by re-running `z3rno-evals run` against a
better-configured server and committing the fresh `results.json`.
